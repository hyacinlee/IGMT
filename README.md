## Introduction

Current release: **v1.1.0**. See [release notes](https://github.com/hyacinlee/IGMT/releases/tag/v1.1.0) for the revision summary.

IGMT provides a set of modules covering phenotype preprocessing, phenotype imputation and clustering, genome-wide association analysis, candidate gene prioritization, gene-level effect estimation, haplotype analysis, BSA, transcriptome–phenotype association, VCF processing, and visualization.

The major modules are:

- **Vcftools**: basic processing of VCF files, including filtering, simplification, and renaming of chromosomes or samples.
    
- **Phenotype**: phenotype matrix processing, missing-value imputation, trait correlation analysis, and trait clustering.
    
- **GWAS**: multi-trait genome-wide association analysis based on EMMAX.
    
- **Evidence**: candidate gene prioritization by integrating GWAS signals, variant annotation, genomic position, eQTLs, and additional multi-omics evidence.
    
- **GeneEffect**: gene-level effect estimation from SNP genotypes using ElasticNet or PCA-based aggregation.
    
- **Candidate**: integration and co-localization analysis of candidate genes obtained from multiple traits or analyses.
    
- **Haplotype**: haplotype analysis for specified candidate genes and comparison of haplotypes with phenotypic variation.
    
- **BulkSegAna**: bulked segregant analysis using Euclidean distance or SNP-index approaches.
    
- **TransAsso**: population-level association analysis between gene expression and phenotypes.
    
- **Visualize**: visualization of GWAS results, phenotype distributions, correlations, PCA, and genotype–phenotype relationships.

## Installation

> **Requirements:** Python >= 3.10  
> **Optional:** PLINK 1.9 and EMMAX are only required for the GWAS module.

### 1. Download the source

Download the source before installing requirements or building the image. All subsequent commands assume that the current directory is the cloned IGMT repository root.

```bash
git clone https://github.com/hyacinlee/IGMT.git
cd IGMT
```

### 2. Set up the Python environment

**Option 1 — pip**

If Python >= 3.10 is already available:

```
pip3 install -r requirements.txt
```

**Option 2 — Conda (recommended)**

```
conda create -n IGMT -c conda-forge -c bioconda \
    python=3.10 numpy scipy pandas scikit-learn statsmodels \
    matplotlib seaborn cyvcf2 joblib

conda activate IGMT
```

**Option 3 — Building the Docker image** (can be used directly without any additional installation).
```
docker build -t igmt:v1.1.0 .

docker run --rm igmt:v1.1.0
```

The commands below use a native `IGMT.py` executable. With Docker, pass the module and arguments after the image name, and mount the working directory to retain output files. For example, from the repository root:

```bash
docker run --rm \
    -v "$PWD:/work" -w /work \
    igmt:v1.1.0 Phenotype \
    -p example/demo_input.phe --stat -o demo_phenotype
```

The image contains PLINK and EMMAX at the module defaults; native host installation paths should not be passed into the container.


For Option 1 or 2, the **GWAS module** also requires the following external software:

- [PLINK 1.9](https://www.cog-genomics.org/plink/)
- [EMMAX](https://csg.sph.umich.edu/kang/emmax/download/index.html)

### 3. Configure native command paths

For a native Python installation (Option 1 or 2), add IGMT to your current shell environment:

```
export PATH="$(pwd):$PATH"
export PYTHONPATH="$(pwd)/src:$PYTHONPATH"
```

For permanent configuration, add the following to `~/.bashrc` after replacing `/absolute/path/IGMT` with the actual checkout path. Do not leave `$(pwd)` in a startup file, because a new shell may start in a different directory.

```bash
export PATH="/absolute/path/IGMT:$PATH"
export PYTHONPATH="/absolute/path/IGMT/src:$PYTHONPATH"
```


### 4. Test the installation

```
IGMT.py -h
```

For options of a specific module, use `IGMT.py MODULE -h` and replace MODULE with its name.

For example:

```
IGMT.py Phenotype -h
IGMT.py GWAS -h
IGMT.py Evidence -h
```

# 1. Vcftools

The `Vcftools` module provides lightweight VCF preprocessing functions required by downstream IGMT analyses. It is intended for common format-processing operations rather than as a replacement for specialized VCF-processing software.

### Example

These preprocessing steps are optional and should be run only when needed for your own VCF files. The supplied `demo_input.vcf.gz` has already been formatted for the downstream examples; users can skip this section when using the demo dataset.

For chromosome renaming, `chromosome.rename.txt` is a whitespace-delimited, two-column file without a header. The first column contains the old chromosome ID (as it appears in the input VCF), and the second column contains the new ID:

```text
chr01    1
chr02    2
```

Replace these illustrative IDs with your own old-to-new mappings. Include every chromosome you want to retain: chromosomes absent from this file are discarded when `--rename_chr` is used. Keep the new IDs consistent with the downstream annotation and gene-position files.

```bash
# Rename chromosomes (only if needed)
IGMT.py Vcftools \
    -v input.vcf \
    --rename_chr \
    --chr chromosome.rename.txt \
    -o output.rename.vcf

# Add SNP IDs if they are missing, as SNP IDs are required for GWAS analysis.
IGMT.py Vcftools \
    -v output.rename.vcf \
    --add_ids \
    -o output.add.vcf
```

### Main parameters

|Parameter|Description|
|---|---|
|`-v, --vcf`|Input VCF file|
|`-c, --chr`|Chromosome list or chromosome-renaming file|
|`-k, --keep`|Sample list or sample-renaming file|
|`-t, --tags`|FORMAT fields to retain, such as `GT AD DP`|
|`-o, --out`|Outfile name|
|`-a,--add_ids`|Generate SNP IDs in `chromosome_position` format|
|`--simplify`|Remove unnecessary VCF information and retain genotype information|
|`--rename_chr`|Rename chromosomes according to `--chr`|
|`--rename_sample`|Rename samples according to `--keep`|
|`--diploid`|Convert haploid genotypes to pseudo-diploid genotypes|

### Parameter selection

These parameters mainly control file formatting and therefore do not affect statistical inference. Users should retain the FORMAT fields required by subsequent analyses and ensure that chromosome and sample identifiers are consistent among genotype, phenotype, covariate, and annotation files.

### Result interpretation

The output is a processed VCF file. Before downstream analysis, users should confirm that chromosome names, SNP IDs, sample IDs, and genotype FORMAT fields are consistent with the corresponding phenotype and annotation files.

# 2. Phenotype

The `Phenotype` module performs phenotype matrix (Samples x Traits, see `example/demo_input.phe`) preprocessing, missing-value imputation, correlation analysis, and trait clustering. It is designed particularly for large phenotypic datasets containing many correlated traits.

## 2.1 Basic matrix operations

Run these commands from the IGMT repository root. In `example/demo_input.phe`, rows represent samples and columns represent traits, with sample IDs in the first column and trait names in the header.

`Candidate.sample.ids` and `Candidate.traits.ids` are one-column plain-text files without a header, with one ID per line. IDs must exactly match the phenotype sample IDs or trait names, respectively. `--subLines` extracts sample rows; `--subColumns` extracts trait columns.

For example, `example/Candidate.sample.ids` contains:

```text
1
2
3
4
5
```

The supplied `example/Candidate.traits.ids` contains:

```text
Trait1
Trait2
Trait3
Trait4
Trait5
```

Expected outputs are `Candidate.samples.sub_set.tsv` (selected samples), `Candidate.traits.sub_set.tsv` (selected traits), and `demo_phenotype.stat_row.tsv` (sample-wise statistics).

```bash
# Extract samples (rows)
IGMT.py Phenotype \
    -p example/demo_input.phe \
    --subLines example/Candidate.sample.ids \
    -o Candidate.samples

# Extract traits (columns)
IGMT.py Phenotype \
    -p example/demo_input.phe \
    --subColumns example/Candidate.traits.ids \
    -o Candidate.traits

# Calculate row-wise statistics
IGMT.py Phenotype \
    -p example/demo_input.phe \
    --stat \
    -o demo_phenotype

```

The module also supports matrix merging, transposition, replicate averaging, correlation calculation, and group-based t-tests.

## 2.2 Missing-value imputation

IGMT implements two iterative imputation strategies:

- `iterative_rf`: iterative random-forest regression
    
- `iterative_bayes`: iterative Bayesian regression
    

For each phenotype with missing observations, other traits correlated with the target phenotype are selected as predictors. Predictor selection is controlled by the correlation threshold and the maximum number of predictors.

### Example

The original `example/demo_input.phe` contains no missing values. The supplied `example/demo_input.masked.phe` has 5% of the observed entries replaced with `NA` using random seed 42. Sample IDs, trait names, and unmasked values are unchanged. `example/demo_input.masked.truth.tsv` records the masked sample/trait coordinates and original values; `example/demo_input.masked.metadata.json` records masking settings.

Use the truth table only to evaluate predictions at artificially masked entries. Do not supply it as an imputation input or reference database. Some masked values may remain missing if no eligible predictors are available.

```bash
IGMT.py Phenotype \
    -p example/demo_input.masked.phe \
    --impute iterative_rf \
    --top_k 10 \
    --corr_threshold 0.7 \
    --n_iter 5 \
    -o phenotype.imputed
```

Optional: an external phenotype or multi-dimensional reference matrix can also be supplied. This requires a user-prepared reference.matrix.tsv (tab-delimited samples x reference traits, with a header and matching sample IDs in the first column). Reference-trait names should differ from target-trait names. This file is not required for the self-contained example above:

```bash
IGMT.py Phenotype \
    -p example/demo_input.masked.phe \
    --impute iterative_rf \
    --database reference.matrix.tsv \
    --top_k 10 \
    --corr_threshold 0.7 \
    -o phenotype.imputed.reference
```

### Important parameters

|Parameter|Default|Description|
|---|--:|---|
|`--impute`|—|`iterative_rf` or `iterative_bayes`|
|`--corr_threshold`|0.6|Minimum correlation required for a trait to be considered as a predictor|
|`--top_k`|10|Maximum number of the most strongly correlated predictor traits|
|`--n_iter`|5|Maximum number of iterative imputation rounds|
|`--threads`|24|Number of parallel threads|
|`--database`|None|Optional external matrix used to provide predictor traits|

### Parameter selection and expected effects

`--corr_threshold` controls how strongly related a predictor must be to the target phenotype. A higher threshold selects fewer but more strongly correlated traits, whereas a lower threshold increases the number of available predictors but may introduce weakly informative variables.

`--top_k` limits the maximum number of correlated traits used for prediction. Increasing this value provides more predictors when many related traits are available, but does not necessarily improve imputation when additional traits are weakly related.

`--n_iter` controls the maximum number of iterative updating rounds. The default value is suitable for routine analyses; increasing it may be useful when missingness is extensive but also increases computation time.

Because correlation structures differ substantially among datasets and traits, the default parameters should be regarded as practical starting values rather than universally optimal settings. For important datasets, users are encouraged to evaluate several combinations of `--corr_threshold` and `--top_k`, for example by artificially masking a subset of observed values and comparing imputation accuracy.

### Result interpretation

The self-contained example produces `phenotype.imputed.tsv` and `phenotype.imputed.log`. The optional reference example uses a separate `phenotype.imputed.reference` prefix to avoid overwriting them. The main output is the completed phenotype matrix. Imputed values should not automatically be considered equivalent to directly measured observations. For downstream analyses, users should examine the proportion of missing values, the number and strength of available predictor traits, and, where possible, evaluate imputation accuracy using masked observed values.

Traits with few or no sufficiently correlated predictors may be less reliably imputed than traits embedded in strongly correlated phenotype groups.

## 2.3 Trait clustering

IGMT implements iterative correlation–principal component clustering to group highly correlated phenotypes and reduce redundant traits in large-scale phenotype datasets.

### Global clustering

```bash
IGMT.py Phenotype \
    -p example/demo_input.phe \
    -g \
    -c 0.7 \
    -z 0.8 \
    -b 500 \
    -o phenotype.C70.Z80
```

### Local clustering
`example/demo_local.txt` specifies the traits used to initiate local clustering. It is a one-column plain-text file without a header, with one trait name per line. Names must exactly match the phenotype header. For example:

```text
Trait1
Trait2
Trait3
Trait4
Trait5
```

IGMT starts clustering from these selected traits and searches the phenotype matrix for correlated traits that satisfy the correlation and PC1 thresholds. The list specifies starting traits, rather than restricting all cluster members to the listed traits.


```bash
IGMT.py Phenotype \
    -p example/demo_input.phe \
    -l example/demo_local.txt \
    -c 0.7 \
    -z 0.8 \
    -b 500 \
    -o phenotype.C70.Z80.local
```

### Important parameters

|Parameter|Default|Description|
|---|--:|---|
|`-g, --globals`|—|Perform clustering for all traits|
|`-l, --locals`|—|Perform clustering around specified traits|
|`-c, --corr_threshold`|0.6|Minimum pairwise correlation used when constructing a candidate group|
|`-z, --pc_threshold`|0.8|Minimum PC1 contribution required for retaining traits in a cluster|
|`-b, --bootstrap`|500|Number of repeated clustering iterations|
|`--cluster_selection`|`min_groups`|Select the run with the fewest groups (`min_groups`) or the highest weighted mean PC1 (`max_pc1`)|
|`-f, --fig`|False|Output correlation heatmaps for resulting groups|

### Parameter selection and expected effects

The correlation threshold (`-c`) controls the initial similarity required among traits. Increasing this threshold generally produces smaller and more homogeneous groups, whereas decreasing it allows more moderately correlated traits to enter the same candidate group.
   
The PC1 threshold (`-z`) controls the amount of common variation that must be captured by the first principal component. A higher value imposes a stricter requirement for within-group consistency.

Because the procedure begins from iteratively selected base traits, `-b` repeats the clustering process and reduces uncertainty associated with a particular starting order. The default of 500 iterations is recommended for final analyses; fewer iterations can be used during exploratory testing.

By default, `--cluster_selection min_groups` selects the run with the fewest total groups, including singleton groups, to maximize dimensionality reduction subject to the specified clustering thresholds. Alternatively, `--cluster_selection max_pc1` selects the highest trait-number-weighted mean PC1 variance explained across multi-trait groups, retaining the previous selection rule.

For the PC1 criterion, singleton groups are excluded and the mean is calculated as `sum(group_size * PC1) / sum(group_size)` over groups containing at least two traits. Runs without multi-trait groups rank after runs with a defined mean; if all runs lack multi-trait groups, the earliest run is retained. Exact ties under any criterion retain the earliest run. The selected criterion and iteration are printed in the log, and per-group iteration records remain available in `*.best_history.tsv` (or `*.locals_best_history.tsv`). The same selection option applies to global and local clustering.

```bash
# Fewest groups (default)
IGMT.py Phenotype -p example/demo_input.phe -g -c 0.7 -z 0.8 -b 500 --cluster_selection min_groups -o phenotype.min_groups

# Previous selection rule: highest weighted mean PC1
IGMT.py Phenotype -p example/demo_input.phe -g -c 0.7 -z 0.8 -b 500 --cluster_selection max_pc1 -o phenotype.max_pc1
```

### Result interpretation

Each resulting group represents a set of phenotypes sharing substantial correlation and a common major variation component. A group containing many traits indicates a strong redundant or coordinated phenotype pattern, whereas isolated traits generally represent relatively independent phenotypic variation.

The derived principal-component phenotype can subsequently be used as a representative phenotype in GWAS, reducing the number of highly redundant association tests.

# 3. GWAS

The `GWAS` module performs genome-wide association analysis for one or multiple phenotypes using EMMAX.

- Ensure that **EMMAX** and **PLINK 1.9** are installed on the system. 
- Use `--emmax` to specify the directory containing the `emmax-intel64` and `emmax-kin-intel64` executables
- Use `--plink` to specify the direct path to the **PLINK 1.9** executable.
- `-c`: Specifies the covariate matrix. The file should not contain a header, and the first column must contain sample IDs (see `example/demo_input.PCA.cov`).
- The phenotype and VCF are matched by sample ID; samples absent from either are excluded. If `-c` is supplied, it must contain every retained sample ID. Covariate rows can appear in a different order.

### Basic analysis

Run from the IGMT repository root. The supplied VCF, phenotype, and covariate files use matching sample IDs. `example/demo_input.PCA.cov` contains sample IDs followed by numeric PCA covariates, without a header. Replace the PLINK and EMMAX paths below with their installed locations on your system.

```bash
IGMT.py GWAS \
    -v example/demo_input.vcf.gz \
    -p example/demo_input.phe \
    -c example/demo_input.PCA.cov  \
    --plink ~/software/reseq/plink1.9/plink \
    --emmax ~/software/reseq/EMMAX/
```

The following is an alternative to the basic command, not a second step. Choose one GWAS command for a clean working directory: GWAS uses fixed intermediate names and completion markers, so existing files must not be reused when changing input data or split mode. The `-o` option does not create a separate output directory.

For large VCF files, chromosomes can be processed separately:
- `example/chrom.lst`: A text file without a header containing one chromosome ID per line, matching the first column of the supplied VCF.
```bash
IGMT.py GWAS \
    -v example/demo_input.vcf.gz \
    -p example/demo_input.phe \
    -c example/demo_input.PCA.cov \
    --split example/chrom.lst \
    --plink ~/software/reseq/plink1.9/plink \
    --emmax ~/software/reseq/EMMAX/ \
    --threads 24
```


### Important parameters

|Parameter|Default|Description|
|---|--:|---|
|`-v, --vcf`|—|Input genotype VCF(.vcf or .vcf.gz)|
|`-p, --phe`|—|Phenotype file|
|`-c, --cov`|None|Covariates such as principal components or population structure|
|`-m, --maf`|0.05|Minimum minor allele frequency|
|`-s, --sign`|B|Significance threshold|
|`-t, --threads`|12|Number of parallel threads|
|`--split`|None|Chromosome list for chromosome-wise parallel analysis|

For `--sign`:

- `B`: `1 / number_of_SNPs`
    
- `F`: `0.05 / number_of_SNPs`
    
- a numeric value: user-defined P-value threshold
    

### Parameter selection and expected effects

The MAF threshold removes rare variants with insufficient genotype counts for reliable association testing. Lowering the threshold retains more rare variants but may reduce statistical stability, particularly in populations with modest sample sizes.

Population structure or other relevant covariates should normally be included using `-c` to reduce confounding.

`--split` changes computational efficiency  and is recommended for very large genotype datasets.

### Main outputs and interpretation

For each trait (`{trait}`) in the phenotype file, the `GWAS` module generates the following output files:
- `Traits.{trait}.emmax.ps.tsv.gz`: Standard GWAS results containing `Chrom`, `Pos`, `ID`, `Value`, `Beta`, `SE`, and `R2`.
- `Traits.{trait}.emmax.ps.significant.tsv`: Information on significant SNPs identified in the GWAS.
- `Traits.{trait}.phe`: Headerless, three-column per-trait phenotype file: sample ID, repeated sample ID, and phenotype value. Evidence, GeneEffect, Haplotype, and Visualize pvg use this file.
- `Traits.{trait}.manhattan.png`: Manhattan plot of the GWAS results.

Lower P-values indicate stronger evidence for phenotype–genotype association. SNPs with P-values at or below the selected significance threshold are written to significant-site output files and can be passed directly to the `Evidence`, `GeneEffect`, or `Haplotype` modules.

Genome-wide significance should be interpreted together with local LD structure, allele frequency, population structure, and biological annotation rather than solely from the most significant SNP.

# 4. Evidence

The `Evidence` module prioritizes candidate genes by integrating significant GWAS SNPs with variant functional annotation, physical distance to genes, eQTL information, and optional additional biological evidence.

### Example

Run these commands from the repository root after GWAS. Trait512 and Trait516 correspond to TL_cmp1298 and YL_cmp1298 in this demo. Each uses its own significant-SNP table and three-column phenotype file generated by GWAS.

The required variant annotations are supplied as `example/demo_input.variant_function` and `example/demo_input.exonic_variant_function`; pass their shared prefix to `-a`. The indexed VCF and the other evidence inputs are also included in `example/`. No separate ANNOVAR preparation is needed for this demo.

```bash
for trait in Trait512 Trait516; do
    IGMT.py Evidence \
        -i Traits.${trait}.emmax.ps.significant.tsv \
        -v example/demo_input.vcf.gz \
        -a example/demo_input \
        -b example/demo_gene.bed \
        -f example/demo_Function.txt \
        -e example/demo_eQTL.txt \
        -p Traits.${trait}.phe \
        -w example/demo_weight.txt \
        --regions 1 200 \
        --regions_score 2 1 \
        -o Traits.${trait}
done
```


WeightGenes is sorted by Total_score; this ranks supporting evidence and does not establish causality.

### Core evidence parameters

- `-i,`: Candidate SNP results. This file can be generated from the output of the `GWAS` module.
- `-p`: Phenotype file. This file can also be obtained from the `GWAS` module output.
- `-v`: Input VCF file. Only gzip-compressed VCF (`.vcf.gz`) is supported. The VCF must be indexed using **tabix** or **bcftools**, with a corresponding `.tbi` or `.csi` index file.
- `-a`: Prefix SNP annotation results generated by **ANNOVAR** , files  {a}.variant_function  and   {a}.exonic_variant_function will be read.
- `-b`: Tab-delimited BED-like file containing gene or mRNA coordinates. The file must contain at least five columns in the following order: `Chrom`, `start`, `end`, `strand`, and `gene_name`. See `example/demo_gene.bed` for an example
- `-f`: Gene functional annotation file with a header. The first column contains gene IDs (named `Gene_ID` in the supplied file), and additional annotation columns can be included. See `example/demo_Function.txt` for an example.


|Parameter|Default|Description|
|---|--:|---|
|`--snp_scores`|`10 5 3 2`|Weights for nonsynonymous, synonymous, intronic, and splicing SNP categories|
|`--regions`|`100`|Distances from associated SNPs to nearby genes, in kb|
|`--regions_score`|`1`|Weight assigned to each distance category|
|`--eQTL_score`|3|Weight assigned to SNP–gene eQTL evidence, See `example/demo_eQTL.txt` for an example|
|`--base_scores`|0.8|Relative contribution of genetic evidence to the final integrated score|
|`--min_sites`|5|Minimum number of candidate SNPs required to continue analysis|
|`--max_sites`|200|Maximum candidate SNPs retained, ranked by increasing P-value; values <= 0 disable the cap|
|`-w, --weight`|None|Optional additional evidence and corresponding weights|

The number of values supplied to `--regions_score` must match the number supplied to `--regions`.

### Interpretation of the default weights

The default SNP-category weights represent the expected relative functional importance of different forms of genetic evidence rather than statistically estimated effect sizes. Therefore, nonsynonymous variants receive a larger default contribution than synonymous, intronic, or nearby variants.

These values can be modified according to the biological context and the type of available data.

### Additional evidence

The supplied `example/demo_weight.txt` contains the following weights and paths (resolved from the repository root):

```text
#Name       Type       Weight    File
Expression  express    5         example/demo_input.expression.tsv
SV          loci       3         example/demo_structural_variants.bed
DEG         gene       2         example/demo_Diff_gene.lst
```

Supported evidence types include:

- `express`: gene-expression evidence, See `example/demo_input.expression.tsv` for an example
    
- `loci`: genomic interval evidence, See `example/demo_structural_variants.bed` for an example
    
- `gene`: candidate-gene list evidence, See `example/demo_Diff_gene.lst` for an example
    

Input formats for additional evidence (without headers):

- eQTL: two columns, SNP ID and target gene ID.
- SV/loci: four columns, chromosome, start, end, and interval ID.
- DEG/gene: three tab-separated columns, gene ID, numeric evidence value, and annotation (for example `W02g004304 1 Up`). A one-column gene list is insufficient.
- Expression: a headered genes x samples matrix, with gene IDs in the first column and matching sample IDs in the remaining column names. Missing expression contributes zero to the evidence score.

The relative contributions of individual additional evidence types can be modified using the `Weight` column.

### Combining genetic and additional evidence

When additional evidence is supplied, IGMT calculates:

```text
Total_score =
    base_scores × Base_score
    + (1 - base_scores) × Evi_score
```

The default `--base_scores 0.8` therefore gives greater weight to the original genetic evidence while allowing complementary multi-omics information to modify candidate-gene ranking.

Increasing `--base_scores` makes the ranking more dependent on GWAS and variant evidence; decreasing it increases the influence of additional biological evidence.

### Main outputs

For each trait, the command produces SNP-level annotation, basic candidate-gene scores, and integrated candidate-gene scores. For example, Trait512 produces the following suffixes with the prefix `Traits.Trait512`:

```text
*.sign.BasicSite.xls
*.sign.BasicGene.xls
*.sign.BasicGT.lst
*.sign.WeightGenes.xls
*.sign.vaildSite.xls
```

`BasicSite` summarizes associated SNPs, their functional classes, mapped genes, distance information, and GWAS statistics.

`BasicGene` summarizes SNP-based evidence at the gene level and reports a `Base_score`.

`BasicGT` contains five leading columns (ID, Chrom, Pos, Ref, Alt), followed by sample genotype columns, and is passed directly to GeneEffect and Visualize pvg. `vaildSite` (the current output spelling) records the candidate SNPs actually retained for Evidence.

When additional evidence is provided, `WeightGenes` reports the integrated `Total_score`, together with genetic and additional evidence scores.

### Result interpretation

Genes with larger `Base_score` have stronger support from the underlying GWAS-associated variants and their functional categories.

Genes with larger `Total_score` receive stronger combined support after incorporating additional evidence. Candidate genes should normally be interpreted by considering both the final ranking and the specific evidence contributing to that ranking rather than treating the score as a probability of causality.

# 5. GeneEffect

The `GeneEffect` module estimates the phenotypic contribution of SNPs assigned to each gene. SNPs are first filtered according to LD and are then summarized using either ElasticNet regression or PCA before estimating gene-level phenotype variance.

### Example

Use the BasicSite and BasicGT files from the Evidence command above, together with the matching GWAS phenotype and demo covariates.

```bash
IGMT.py GeneEffect \
    -s Traits.Trait512.sign.BasicSite.xls \
    -g Traits.Trait512.sign.BasicGT.lst \
    -p Traits.Trait512.phe \
    -c example/demo_input.PCA.cov \
    --method ElasticNet \
    --ld-r2 0.9 \
    --min-snps 1 \
    -o Traits.Trait512
```

The command produces `Traits.Trait512.gene_effect.ElasticNet.tsv` and the corresponding sample-by-gene score matrix.

### Important parameters

|Parameter|Default|Description|
|---|--:|---|
|`--method`|ElasticNet|SNP aggregation method: `ElasticNet` or `PCA`|
|`--ld-r2`|0.9|LD threshold used for SNP pruning within genes|
|`--min-snps`|1|Minimum number of SNPs required per gene after pruning|
|`--l1-ratio`|0.5|ElasticNet mixing parameter|
|`-c, --cov`|None|Optional covariates|

### Parameter selection and expected effects

A lower `--ld-r2` applies more stringent LD pruning and reduces redundancy among SNPs, whereas a higher threshold retains more correlated SNPs.

`ElasticNet` is suitable when multiple SNPs may jointly contribute to the phenotype and provides regularized SNP weighting. `PCA` provides a simpler representation of the major genotype variation within each gene.

The default `--l1-ratio 0.5` balances L1 and L2 regularization. Users generally do not need to modify this value unless they specifically wish to change the sparsity of SNP effects.

### Result interpretation

The primary output is:

```text
*.gene_effect.ElasticNet.tsv
```

or the corresponding PCA output.

Genes with larger gene-level explained-effect statistics contribute more strongly to phenotypic variation in the analyzed population. These estimates provide a complementary ranking to SNP-level GWAS significance and the evidence-based ranking produced by the `Evidence` module.

A high gene-level effect does not by itself establish causality and should be interpreted together with GWAS significance and biological evidence.

# 6. Candidate

The `Candidate` module integrates candidate-gene results across multiple traits and identifies genes repeatedly supported by related phenotypes.

### Input file

The supplied `example/demo_Coloc.txt` lists the two WeightGenes outputs produced above. It has no header: each line contains a trait name and its candidate-gene result path.

```text
Trait512    Traits.Trait512.sign.WeightGenes.xls
Trait516    Traits.Trait516.sign.WeightGenes.xls
```

### Example

```bash
IGMT.py Candidate \
    -i example/demo_Coloc.txt \
    --co_local \
    --fit_exp "Expression !=None" \
    -o TraitGroup
```

The filter keeps genes with non-missing expression evidence; `None`, `NA`, and empty values are treated as missing.

The outputs contain filtered trait-gene records and a gene-level summary across the supplied traits.

### Main parameters

|Parameter|Description|
|---|---|
|`--co_local`|Integrate candidate genes across multiple traits|
|`--fit_exp`|Filter input candidate tables using a specified column expression|
|`-o`|Output prefix|

### Result interpretation

The module reports both the merged candidate-gene records and a gene-level summary across traits.

Genes supported by multiple related traits may represent shared genetic regulators or pleiotropic candidate genes. However, repeated detection among correlated phenotypes should not automatically be interpreted as independent evidence; the result is intended primarily for prioritization.

# 7. Haplotype

The `Haplotype` module performs candidate-gene-level haplotype analysis using GWAS SNPs and genotype data and relates the resulting haplotypes to phenotypic values.

### Example

This example uses the complete GWAS result for Trait512 and W07g016057, the top-ranked gene from its Evidence result. The GWAS phenotype file and bundled VCF, annotations, and gene positions are passed directly to Haplotype.

```bash
IGMT.py Haplotype \
    -i Traits.Trait512.emmax.ps.tsv.gz \
    -g W07g016057 \
    -p Traits.Trait512.phe \
    -v example/demo_input.vcf.gz \
    -a example/demo_input \
    -b example/demo_gene.bed \
    -r NoSyn CDS \
    -o Trait512.W07g016057
```

Under the default Hom mode, samples with a heterozygous call at any selected SNP are excluded.

### Important parameters

|Parameter|Default|Description|
|---|--:|---|
|`-g, --gene`|—|Candidate gene|
|`-r, --region`|All|SNP classes included: `All`, `CDS`, `NoSyn`, `intronic`, or `Promoter`|
|`-m, --method`|Hom|Haplotype processing method|
|`-f, --flank`|2000|Promoter flanking distance in bp|

### Parameter selection

`--region` determines which variants are used to define haplotypes. Restricting the analysis to coding or nonsynonymous variants provides a more functionally focused analysis, while `All` retains the maximum available genetic information.

### Main outputs and interpretation

Typical outputs include:

```text
*.Site_info.txt
*.hap_info.txt
*.sample_hap.txt
```

`Site_info` describes the variants used to construct haplotypes, `hap_info` summarizes haplotype groups and their phenotype information, and `sample_hap` reports the haplotype assigned to each sample.

Phenotypic differences among haplotypes provide supporting evidence that local genetic variation around a candidate gene is associated with the trait.

# 8. BulkSegAna

The `BulkSegAna` module performs bulked segregant analysis using either Euclidean distance (`ed`) or SNP-index (`index`).

### Single-site analysis

```bash
IGMT.py BulkSegAna \
    -v snp.filter.vcf \
    -s1 Low \
    -s2 High \
    -t ed \
    -s top1
```

### Sliding-window analysis

```bash
IGMT.py BulkSegAna \
    -v snp.filter.vcf \
    -s1 Low \
    -s2 High \
    -t ed \
    -step 50 \
    -wind 500 \
    -minSite 5 \
    -minDepth 10
```

### Important parameters

|Parameter|Default|Description|
|---|--:|---|
|`-t`|ed|`ed` or `index`|
|`-step`|None|Sliding-window step size in kb|
|`-wind`|None|Sliding-window size in kb|
|`-minDepth`|10|Minimum sequencing depth in each bulk|
|`-minSite`|10|Minimum number of SNPs per window|
|`-s`|top1|Candidate-region threshold|

Smaller windows provide higher spatial resolution but contain fewer SNPs and may therefore be noisier. Larger windows provide smoother signals but reduce localization resolution.

Candidate regions are represented by genomic intervals showing unusually large differences between the two bulks.

# 9. TransAsso

The `TransAsso` module tests associations between population-level gene-expression variation and phenotypic variation using linear regression.

### Example

The supplied expression matrix uses the same sample IDs as the phenotype and covariate files. Rows are genes, columns are sample IDs, and the first column is GeneID.

```bash
IGMT.py TransAsso \
    -e example/demo_input.expression.tsv \
    -p example/demo_input.phe \
    -c example/demo_input.PCA.cov \
    --threads 24
```

The command above analyzes all traits. Specific traits can be selected using:

```bash
IGMT.py TransAsso \
    -e example/demo_input.expression.tsv \
    -p example/demo_input.phe \
    -t Trait512 Trait516 \
    -c example/demo_input.PCA.cov
```

Outputs are `TransAsso.Trait512.txt`, `TransAsso.Trait512.signal.txt` and corresponding Trait516 files.

### Important parameters

|Parameter|Description|
|---|---|
|`-e, --express`|Gene-expression matrix|
|`-p, --phe`|Phenotype matrix|
|`-c, --cov`|Covariates|
|`-t, --trait`|Traits to analyze; all traits are analyzed if omitted|
|`-l, --loci`|Optional gene-position file|
|`--threads`|Parallel threads|
|`--figGenes`|Genes for which expression–phenotype plots should be generated|

### Parameter selection

Although covariates are optional, population-structure or other appropriate covariates are strongly recommended when expression and phenotype data are measured in a structured population.

### Result interpretation

Genes with small association P-values show expression levels that covary with the phenotype after accounting for the supplied covariates.

Such associations provide transcriptomic support for candidate genes but do not distinguish whether expression variation is causal, consequential, or correlated with another underlying factor.

# 10. Visualize

The `Visualize` module supports Manhattan plots (`manha`), genotype-phenotype comparisons (`pvg`), and general statistical plots (`stat`). Run the following commands from the repository root after the Trait512 GWAS and Evidence examples above.

### Manhattan plot

The GWAS `Value` column contains raw P-values, so `--log` converts them to -log10(P). `example/demo_visualize.highlight.tsv` is a three-column file without a header: SNP ID, label, and color. The supplied line is:

```text
chr7_49186818    W07g016057    red
```

```bash
IGMT.py Visualize \
    -m manha \
    --site_value Traits.Trait512.emmax.ps.tsv.gz \
    --hightlight example/demo_visualize.highlight.tsv \
    --log \
    -o Trait512.visualize
```

Expected output: `Trait512.visualize.manhattan.png`. The marker ID must match the GWAS ID column. `--sign`, `--sub`, and `--local` control the threshold, chromosome subset, and genomic interval.

### Genotype-phenotype comparisons

`example/demo_visualize.snps.ids` is a one-column file without a header, with one SNP ID per line; the supplied file contains `chr7_49186818`. Use the matching Evidence genotype file and three-column GWAS phenotype file:

```bash
IGMT.py Visualize \
    -m pvg \
    --snps example/demo_visualize.snps.ids \
    --gt Traits.Trait512.sign.BasicGT.lst \
    -p Traits.Trait512.phe \
    -o Trait512.pvg
```

Expected outputs:

- `Trait512.pvg.chr7_49186818.Phe_by_GT.pdf`: automatic pairwise t-tests and a boxplot.
- `Trait512.pvg.phe.gt.info.xls`: the joined Sample, Phenotype, and SNP-genotype table used by the next example.

The pvg mode writes PDF plots.

### Specify comparison groups for the boxplot

Reuse the joined table from the previous command. Each `--ttest` argument contains two observed genotype labels separated by a comma.

```bash
IGMT.py Visualize \
    -m stat \
    --df Trait512.pvg.phe.gt.info.xls \
    --box \
    --xData chr7_49186818 \
    --yData Phenotype \
    --ttest AA,GG AA,AG \
    --figsize 8 8 \
    -o Trait512.chr7_49186818
```

Expected output: `Trait512.chr7_49186818.boxplot.png`.

### Correlation heatmap

First extract a small trait matrix. `example/demo_visualize.traits.ids` contains five trait names, one per line without a header: Trait512, Trait516, Trait349, Trait408, and Trait853.

```bash
IGMT.py Phenotype \
    -p example/demo_input.phe \
    --subColumns example/demo_visualize.traits.ids \
    -o Trait512.cor.traits

IGMT.py Visualize \
    -m stat \
    --df Trait512.cor.traits.sub_set.tsv \
    --cor \
    --plot Col \
    --figsize 8 8 \
    -o Trait512.cor
```

`--plot Col` calculates correlations between trait columns. Expected outputs are `Trait512.cor.cor_Col.png` and `Trait512.cor.cor_matrix.tsv`.

### Main visualization parameters

|Parameter|Default|Description|
|---|--:|---|
|`--figsize`|16 5|Figure dimensions|
|`--dpi`|300|PNG resolution|
|`--ftype`|png|`png` or `pdf`|
|`--sign`|B|Manhattan-plot significance threshold|
|`--local`|None|Plot a specified genomic interval|
|`--hightlight`|None|Highlight specified SNPs|
|`--cor`|False|Correlation heatmap|
|`--pca`|False|PCA visualization|
|`--box`|False|Boxplot|
|`--lm_dot`|False|Linear-regression scatter plot|

Visualization parameters affect presentation rather than the statistical analyses themselves.

# Recommended workflow

A typical large-scale phenotypic GWAS workflow in IGMT is:

```text
Phenotype preprocessing
        ↓
Missing-value imputation
        ↓
Trait correlation / clustering
        ↓
GWAS
        ↓
Evidence-based candidate gene prioritization
        ↓
GeneEffect / Candidate
        ↓
Haplotype or TransAsso validation
        ↓
Visualization
```

Not every module is required for every dataset. Individual modules can be used independently according to the available data and the biological question.

## Parameter considerations

The default parameters distributed with IGMT are intended to provide practical starting points for routine analyses. They should not be considered universally optimal for all datasets.

In particular:

- phenotype imputation parameters should be selected according to trait correlation structure and missing-data patterns;
    
- trait-clustering thresholds determine the balance between cluster size and within-cluster consistency;
    
- GWAS thresholds and covariates should reflect marker density and population structure;
    
- candidate-gene evidence weights represent user-adjustable biological priorities rather than statistically estimated effect sizes;
    
- additional omics evidence should only be included when the corresponding data are available and biologically relevant.
    

For important analyses, users are encouraged to evaluate parameter sensitivity and retain the parameter settings used for each analysis to facilitate reproducibility.
